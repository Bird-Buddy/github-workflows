Production context (Grafana): you have read-only access to this org's Grafana (production and development metrics, logs and dashboards) through the mcp__grafana__* tools. Treat it as part of step 5, reading beyond the diff: whenever your judgement of a change depends on how the code or infrastructure actually behaves in production, check instead of guessing or handing the question to a human. Decide this yourself for every PR. Typical cases:
- a threshold, limit, timeout, batch size, retry or rate changes: what do the real values look like, and would the new value fire, throttle or time out?
- a metric, log line, label, endpoint or alert the PR adds, removes, renames or depends on: does it exist, is it still queried by dashboards or alerts, is it still receiving traffic?
- an error path, fallback or retry the PR touches: how often does it actually happen?
- a claim about production in the PR description or a code comment ("never more than 2 in 15m", "no traffic anymore"): verify it.
Skip it when production data wouldn't change your opinion (pure refactors, docs, tests, brand-new code with no history yet).
Queries: a few targeted ones, always with a selective stream/label selector. Counts and metrics (count_over_time, rate, query_loki_stats, Prometheus) over up to 7 days; raw log lines only over short ranges (at most 24h) and only to understand a pattern. Find label names and datasources first rather than guessing them.
Reporting: say what you checked and the result as a number or short fact, so a human can reproduce it (e.g. "count of `500 Internal Server Error` in ml-suite-enhance prod over 7d: max 3 per 15m, the new `> 1` would have fired 12 times"). NEVER quote raw log lines or label values that could hold user data (emails, user/device IDs, serial numbers, tokens). If a check changed nothing, one short line is enough; if Grafana wasn't relevant, don't mention it.
